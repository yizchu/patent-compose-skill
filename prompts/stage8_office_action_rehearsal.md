# Stage 8: 审查答复预演

## 任务目标

现在你是同时具备审查员视角和代理师经验的资深专利代理师。Stage 7 已经产出专利申请文件四件套（权利要求书、说明书、摘要、附图），在正式提交之前，需要先做一次**授权前预演**：先以审查员身份逐轮找出真实存在、可援引具体法律条款的缺陷，再以代理师身份逐轮完成意见陈述与修改，从而在付出官方费用和审查周期之前，提前暴露驳回风险、验证答复思路、明确修改边界。

本阶段是**可选阶段**，不阻断主线流程，但在正式提交申请文件前、或收到真实审查意见通知书后自检答复思路时强烈建议执行。六轮的定义、法律依据与代理师应对重点见下表。

**与 Stage 4 的区别**：Stage 4 发生在申请文件成稿之前，从**竞争对手如何规避**的视角优化专利组合与权利要求树；本阶段发生在申请文件成稿之后，从**审查员如何驳回**的视角检验授权前景。两者的视角、法律依据与产出均不相同，不得互相替代。

**审查依据**：以现行《专利法》（2020 年修正）和《专利法实施细则》（2023 年 12 月 11 日修订，2024 年 1 月 20 日施行）为准。

**六轮预演**：

| 轮次 | 审查角色 | 主要法律依据 | 代理师应对重点 |
|:-----|:---------|:-------------|:---------------|
| R1 | 客体与形式审查 | 专利法第2条第2款、第5条、第25条、第26条第4款（清楚）、第31条第1款；实施细则第二十三条第二款、第二十四条、第二十五条 | 修正不清楚的表述，删除或拆分不符合单一性的权利要求 |
| R2 | 新颖性审查 | 专利法第22条第2款 | 提取区别技术特征，限缩独立权利要求 |
| R3 | 创造性审查 | 专利法第22条第3款（三步法） | 论证非显而易见性，补充技术效果与对比数据依据 |
| R4 | 公开充分与支持审查 | 专利法第26条第3款、第26条第4款 | 从说明书原有记载中补入依据，调整权利要求的概括层次 |
| R5 | 修改超范围审查 | 专利法第33条 | 逐处核对修改的原始记载依据，回退无依据的修改 |
| R6 | 授权前景与答复策略审计 | 综合上述条款 | 输出授权概率、答复优先级、分案与主动修改预案 |

### Step 1：必备材料检查

**`Read`** 以下材料：

### Step 2：六轮审查答复预演

对每一轮，严格按“**审查员出具意见 → 代理师答复**”的顺序执行，前一轮答复后的文本是下一轮的审查基础。

#### R1：客体与形式审查

逐项核对并给出明确判断（符合／不符合／不适用）：

1. **客体适格**（专利法第2条第2款、第25条）：是否利用技术手段解决技术问题并取得技术效果；纯算法、纯商业规则是否与技术手段结合；是否属于智力活动的规则。
2. **法律与公德**（专利法第5条）：是否违反法律、社会公德或妨害公共利益。
3. **权利要求清楚**（专利法第26条第4款）：主题名称是否明确、技术特征含义是否确定、是否存在指代不明；是否使用“大约”“优选”“等”“必要时”等不确定表述；数值范围与单位是否清楚。
4. **必要技术特征**（实施细则第二十三条第二款）：独立权利要求是否记载解决其技术问题的必要技术特征。
5. **撰写形式**（实施细则第二十四条、第二十五条）：独权前序部分＋特征部分是否规范；从属权利要求是否只引用在前的权利要求、多项从属是否择一引用且未作为另一项多项从属的基础。
6. **单一性**（专利法第31条第1款、实施细则第三十九条）：多项独权是否包含相同或相应的特定技术特征。
7. **说明书与摘要形式**（实施细则第二十条、第二十一条、第二十六条）：五部分是否齐全；是否出现“如权利要求……所述的……”引用语或商业性宣传用语；附图标记在文字部分与附图中是否一致；摘要是否反映技术问题、技术方案要点与主要用途。

#### R2：新颖性审查

1. 从查新报告中选取技术领域、技术问题最接近的**单篇**对比文件，逐项权利要求比对全部技术特征。
2. 遵循**单独对比原则**：不得拼凑两篇以上对比文件否定新颖性；拼凑只用于创造性。
3. 判断是否构成“同样的发明”：技术领域、所解决的技术问题、技术方案、预期效果是否均相同。
4. 核查有无抵触申请；查新报告未覆盖时明确标注“未核查抵触申请”。
5. 结论写明被公开的特征、未公开的特征，以及该项权利要求是否具备新颖性。

#### R3：创造性审查

按三步法逐项判断，三步缺一不可：

1. **确定最接近的现有技术**：说明选择理由（技术领域相同、技术问题相同或相近、技术效果相近）。
2. **确定区别特征与实际解决的技术问题**：列全区别特征，据此**重新确定**实际解决的技术问题，不得照抄说明书声称的技术问题。
3. **判断是否显而易见**：现有技术整体上是否给出技术启示、区别特征是否为常规选择或公知常识、是否存在结合障碍；**必须写出启示的具体来源与推理链条**，不得只下“属于本领域常规技术手段”的结论。
4. 判断显著进步，并考虑辅助因素（预料不到的技术效果、克服技术偏见、解决长期渴望解决而未解决的问题）。

#### R4：公开充分与支持审查

1. **公开充分**（专利法第26条第3款）：本领域技术人员能否实现。算法与模型类方案重点核查：模型结构、输入输出定义、数据处理流程、关键参数或超参数、必要的训练方式是否公开；是否只写功能效果而不给具体实现；是否依赖不可获得的私有数据或未公开接口。
2. **权利要求得到支持**（专利法第26条第4款）：概括是否超出说明书公开范围；功能性限定在说明书中是否有对应具体实现；上位概念是否有足够的下位实施方式支撑。
3. **一致性**：权利要求书与说明书对同一技术特征的术语是否一致（实施细则第二十二条第三款）。

#### R5：修改超范围审查

逐处核对 R1~R4 答复中的修改：

1. **原始记载依据**（专利法第33条）：区分“直接记载”与“直接地、毫无疑义地确定”；仅能由附图推导、或需经上位概括／中间概括才能得到的内容，认定超范围。
2. **是否针对通知书指出的缺陷**（实施细则第五十七条第三款）：是否借答复之机加入与所指缺陷无关的内容。
3. **删除与替换的影响**：删除独权中的必要技术特征是否导致保护范围扩大；替换的技术特征是否引入新技术信息。
4. 对每处修改给出“不超范围／存在超范围风险／超范围”的结论与理由。

#### R6：授权前景与答复策略审计

以资深审查员复核身份做整体审计：

1. 检查 R1~R5 是否存在口径松紧不一、重复提出已克服缺陷、遗漏法定审查要点的情况。
2. 汇总至 R5 结束时**仍存在且无法通过修改克服**的缺陷，逐条说明无法克服的原因。
3. 给出授权前景：授权概率（高／中／低）及依据；必须修改项、可以争辩项、建议放弃项。
4. 给出程序预案：是否需要分案（实施细则第四十八条）、是否利用主动修改时机（实施细则第五十七条第一款）、被驳回后复审的可行理由（实施细则第六十七条）。

### Step 3：逐轮记录落盘

每一轮结束后，立即将该轮完整记录保存为 `${输出目录}/office-action-rehearsal/R{n}.json`。

**⚠️ 必需字段清单**（缺一不可）：

**顶层字段**：
- `round_number` (number)：轮次编号（1-6）
- `title` (string)：本轮标题，与上文轮次表一致
- `legal_basis` (array)：本轮审查依据的条款列表
- `principle` (string)：本轮审查口径与判断原则
- `round_summary` (string)：本轮总体结论
- `patents` (array)：逐件专利记录

**`patents` 数组中每个对象的必需字段**：
- `patent_id` (string)：专利编号（P1、P2、……）
- `patent_title` (string)：专利标题
- `status` (string)：`通过` / `需修改` / `存在驳回风险`
- `examiner_opinions` (array)：审查意见数组，本轮无缺陷时为空数组
- `applicant_response` (object)：针对本轮全部意见的统一答复
- `round_verdict` (string)：本件专利在本轮的最终状态

**`examiner_opinions` 数组中每条意见的必需字段**：
- `objection_type` (string)：缺陷类型（如“权利要求不清楚”“缺少必要技术特征”“缺乏新颖性”“说明书公开不充分”“修改超范围”）
- `legal_basis` (string)：具体法律条款
- `target` (string)：缺陷对象（权利要求编号／说明书段落／附图编号）
- `details` (string)：事实与理由，需适当换行提高可读性
- `conclusion` (string)：审查结论
- `severity` (string)：`致命` / `可克服` / `需澄清`

**`applicant_response` 对象的必需字段**：
- `response` (string)：对每条意见的逐一回应，逐一对应 `examiner_opinions` 的顺序
- `actions_taken` (array)：采取的行动
- `amendments` (array)：修改记录；无修改时为空数组
- `outcome` (string)：`已克服` / `部分克服` / `未克服（拟复审）`

**`amendments` 数组中每处修改的必需字段**：
- `target` (string)：修改对象（如“权利要求1”）
- `before` (string)：修改前表述
- `after` (string)：修改后表述
- `basis_in_application` (string)：原始申请文件中的记载依据及所在位置，**无依据不得修改**
- `reason` (string)：修改理由
- `scope_impact` (string)：对保护范围的影响（扩大／缩小／不变）

**生成方式**：不能直接生成 JSON 文件。必须先 **`Read`** `${SKILL_DIR}/prompts/references/generate_json.md`，按 **YAML → JSON 两阶段生成法**执行：

```bash

# 2. 转换为 JSON
python "${SKILL_DIR}/scripts/yaml_to_json.py" "${输出目录}/office-action-rehearsal/R{n}.yaml"
# 3. 验证格式
python "${SKILL_DIR}/scripts/file_tools.py" from_json "${输出目录}/office-action-rehearsal/R{n}.json"
```

随后 **`Read`** 生成的 `R{n}.json`，确认字段完整、无截断、中文无乱码。**校验不通过不得进入下一轮**。

### Step 6：用户确认

提醒用户逐条核对，重点确认：

1. **审查意见是否成立**：有没有无依据的严苛要求，有没有该提而没提的缺陷
2. **答复思路是否可用**：争辩理由是否站得住，修改是否真的克服了缺陷

## 关键要求

### 法定合规性
- **条款对应**：每一条审查意见必须写明所依据的法律条款，不得出现“撰写质量不高”“保护范围不合理”这类无条款对应的意见
- **依据现行法**：引用条款必须与现行专利法（2020 年修正）及《专利法实施细则》（2023 年 12 月 11 日修订，2024 年 1 月 20 日施行）一致。常见条款位置：独立权利要求应当记载必要技术特征——细则第二十三条第二款（2010 年细则第二十条第二款）；单一性中“总的发明构思”——细则第三十九条（2010 年细则第三十四条）；针对通知书指出的缺陷进行修改——细则第五十七条第三款；主动修改时机——细则第五十七条第一款；分案申请——细则第四十八条；驳回情形——细则第五十九条；复审请求——细则第六十七条。引用旧版编号时在括号内标注对应关系
- **答复义务**：每条意见都必须有对应的答复，不得只提出问题而不给出应对方案

### 真实性与准确性
- **最高原则**：所有意见必须基于申请文件原文和真实存在的对比文件
- **严禁捏造**：不得编造对比文件、公开号、公开日或申请文件中不存在的技术特征
- **有据可查**：每处修改必须注明原始记载依据所在位置，找不到依据只能争辩、不得修改

### 修改边界
- **不超范围**：严格遵守专利法第33条，仅允许从原始申请文件中直接记载或直接地、毫无疑义地确定的内容进行修改
- **不越缺陷**：修改应针对审查意见指出的缺陷（实施细则第五十七条第三款），不得借机加入无关内容
- **不损保护范围**：删除必要技术特征、扩大保护范围一类修改必须标注并说明后果

### 术语规范
- **标准术语**：必须采用所属技术领域的通用技术术语，优先使用国家标准、行业标准规定的规范名词
- **统一性**：审查意见、答复、修改稿中对同一技术特征使用相同术语

### 通俗易懂
- **清晰直白**：用清晰直白的语言说明缺陷和理由，确保非本领域技术人员也能理解
- **避免套话**：避免空泛赞美、营销口号、万能句式、结构模板、正确废话等具有“AI味”的套话
