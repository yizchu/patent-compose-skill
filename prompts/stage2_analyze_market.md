# Stage 2: 市场分析与初版权利要求树生成

## 任务目标
基于项目分析结果，结合产品规划、竞品分析和未来 3-5 年市场需求的技术方向预判，通过"技术 + 市场"双维度筛选，找出既能保护企业核心优势、又能卡位未来竞争的技术点，生成初版权利要求树。

---

## 工作流程

### Step 1：读取项目分析结果

**`Read`** `${输出目录}/materials/disclosure-v1.md`：完整项目技术交底书，包含所有技术细节和潜在专利点。

**明确了解**：
- 项目的核心技术方案和技术架构
- 已识别的所有潜在专利点及其技术特征
- 每个专利点的来源文件和技术细节
- 项目的技术优势和创新点

**然后询问用户**："请选择市场分析模式：

**模式 A：轻量级市场摸底（推荐用于科研型专利）**
- ✅ 适用场景：凸显创新型、体现科研产出、短时间内无专利落地打算的专利
- 📊 分析重点：快速验证技术是否有实际应用场景，避免完全脱离实际
- ⏱️ 预计耗时：15-30 分钟

**模式 B：市场深度分析（推荐用于产业化专利）**
- ✅ 适用场景：准备产业化落地、有明确商用价值的专利
- 📊 分析重点：全面的需求分析、未来 3-5 年市场趋势、竞品专利布局、用户痛点等
- ⏱️ 预计耗时：60-90 分钟

根据用户选择，进入对应的模式分支：

- **若选择模式 A** → 执行 **[模式A流程]（Step 2L → Step 3L → Step 4 → Step 5）**

- 技术实现的成本和复杂度是否合理
- 与现有技术栈的兼容性如何

#### 2L.3 未来转化潜力初探（可选，1-2 次搜索）

- 未来 2-3 年该技术的发展方向

### Step 4：生成初版权利要求树

**`Read`** `${输出目录}/materials/disclosure-v1.md` 文件和 `${输出目录}/materials/market-report.md`，基于项目分析结果和市场分析结果，构建一棵完整的"权利要求树"，用JSON格式表示，保存至 `${输出目录}/materials/claim-tree-v1.json` 文件，但你不能直接生成一个 JSON 文件，而必须先 `Read` `${SKILL_DIR}/prompts/references/generate_json.md`，根据里面的指南生成。

**对于轻量级模式生成的权利要求树**：
- **独立权利要求的选择**：优先选择技术价值高且有一定应用场景的专利点
- **保护范围的界定**：适度宽泛，为未来可能的技术转化预留空间
- **从属权利要求的布局**：重点保护核心技术创新点
- **特殊设计的标注**：标注能体现技术独特性的特殊设计

**对于重量级模式生成的权利要求树**：
- **独立权利要求的选择**：优先选择"技术 + 市场"双维度评分高的专利点作为独立权利要求
- **保护范围的界定**：结合市场分析中的竞争格局，避免保护范围过窄（给竞争对手留规避空间）或过宽（可能导致无效）
- **从属权利要求的布局**：重点布局具有高竞争壁垒价值和前瞻性的技术特征
- **特殊设计的标注**：对于能形成有效竞争壁垒的特殊设计，必须在 `special claims` 中明确标注

**格式验证**：

生成权利要求树后，必须执行以下命令检查权利要求树的格式是否符合规范：
```bash
python "${SKILL_DIR}/scripts/claim.py" tree_to_claims "${输出目录}/materials/claim-tree-v1.json"
```
若程序报错，需在保持权利要求树内容不变的情况下调整其结构，再执行上述检查命令，**循环此过程直到权利要求树格式符合核心原则为止**。

**验证后必须 Read 完整文件检查内容！** 即使命令无报错，也要确认自动修复（如有）没有改变原始意图，特别是确认最浅层键的数量和具体内容是否等同于原计划中独立权利要求的数量和具体内容。验证和检查不通过不能继续 Step 5！

**权利要求树构建核心原则**：
- **层级清晰**：独立权利要求（即最浅层键）应包含某一技术方向的完整解决方案，从属权利要求逐层细化独立权利要求的具体实现。例如，独权描述方法整体流程，从权A细化独权步骤1的具体实现或特殊设计，从权B细化独权步骤2的具体实现或特殊设计。低层级的权利要求写入 `contains` 字段或 `special claims` 字段。
- **详细描述**：每个权利要求必须有几句话的详细描述，说明特征、作用、具体实现方式等，写入 `description` 字段（字符串类型）。`description` 字段**不可为空**。
- **结构或步骤划分**：若权利要求包含更低层级的权利要求且这些更低层次的权利要求构成结构或步骤划分，写入 `contains` 字段（字典类型）。`contains` 字段的值**至少要有两个**键值对，若只有一个更低层级的权利要求，则不构成步骤或结构划分，应将其融入 `description` 或 `special claims` 字段。若没有结构或步骤划分，则不要添加 `contains` 字段。
- **特殊设计**：若权利要求包含特殊设计，如"知识图谱的实体id有一定规律从而间接携带信息"或"溯源以后，需要先尝试UTF-8解码，如果失败则尝试GBK解码，最后使用base64，保证数据能正常展示"等，写入 `special claims` 字段（列表类型）。与`contains` 字段不同的是，**`special claims` 字段不构成步骤或结构划分**。若没有特殊设计，则不要添加 `special claims` 字段。
- **顺序逻辑**：同一层级的节点，必须按逻辑先后顺序排列，不要照搬分析结果的写作顺序。
- **技术特征完整且无冗余**：`contains`、`description`、`special claims`三个字段需**互斥完备**地展现技术特征的所有必要技术细节，**内容不能存在冗余**。独立权利要求（即最浅层键）不得同时存在 `contains` 字段和 `special claims` 字段。
- **保护范围合理**：不要包含非必要技术特征。另一方面，但凡涉及到数学式、化学反应等公式，尽量使用上位概括代替后写入权利要求，避免直接写入公式。这样可以避免保护范围过窄。
- **竞争壁垒导向**：对于市场分析中识别出的高竞争壁垒价值技术特征，应在权利要求树中予以特别强调，可通过独立的从属权利要求或在 `special claims` 中详细描述来体现

## 关键要求
- **真实性原则**：所有分析必须严格基于项目的真实文件，不得凭空捏造或臆测不存在的技术方案
- **市场导向**：市场分析必须基于真实的搜索结果和数据，禁止凭空编造市场趋势或竞争情报
- **模式适配**：轻量级模式要聚焦应用场景验证，避免过度分析；重量级模式要全面深入，不要遗漏关键维度
- **全面覆盖**：不能遗漏任何技术细节，只有明显属于行业常规实现的内容才可以省略。
- **术语标准**：必须采用所属技术领域的通用技术术语，优先使用国家标准、行业标准规定的规范名词，以及国际专利分类表（IPC）中的标准技术术语。国家有统一规定的自然科学名词，应当采用官方统一术语；无官方规定的，可采用本领域约定俗成的表述，不得自行编造非通用词汇。禁止使用口头俗称、网络热词、行业黑话、非技术类表述替代专业术语。
- **通俗易懂**：用清晰直白的语言描述技术方案，确保非本领域技术人员也能理解，避免空泛赞美、营销口号、万能句式、结构模板、正确废话等具有"AI味"套话。
- **前瞻性与务实性平衡**：既要考虑未来3-5年的技术趋势，又要基于当前项目实际具备的技术能力，不可过度超前或过于保守
- **可操作性**：所有的分析和建议都要能落实到具体的专利撰写策略上，避免空泛的理论分析
