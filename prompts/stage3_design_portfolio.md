# Stage 3: 专利组合生成与权利要求树优化

## 任务目标

现在你是资深专利代理师，根据查新结果和原始权利要求树，决定将项目分成几件专利、每件专利保护什么技术方案。然后通过**博弈对抗**（一方找漏洞攻击，另一方防守改进）来优化专利布局。

**核心原则**：
- 所有技术方案必须严格来自 claim-tree-v1.json，不得在博弈过程中凭空捏造不存在的技术。claim-tree-v1中的最浅层键是独立权利要求，`special claims`和`contains`都是从属权利要求。
- 博弈的目的是**优化权利要求的撰写方式**（扩大保护范围、封堵规避路径、改进从权布局），而不是发明新技术
- 不能无条件拆分，否则会无故增加专利成本，同一件专利可以有多个独立权利要求，但它们必须属于一个总的发明构思（单一性要求）

## 📋 JSON 生成与验证规范

**【重要】在整个 Stage 3 中，每次生成 JSON 文件，都必须遵守以下规范并在生成后立即验证！**

### ✅ 格式要求

1. **必须使用双引号**：所有字符串和字段名必须用 `"double quotes"` 包裹，**不能用单引号**
2. **不能有尾逗号**：数组或对象的最后一个元素后面**不能加逗号**
3. **布尔值小写**：使用 `true/false`，不能是 `True/False` 或 `"true"/"false"`
4. **嵌套层级对齐**：保持正确的缩进（建议2空格或4空格）
5. ⚠️**括号匹配**：所有括号必须成对出现且正确匹配，不要出现未关闭的括号。
6. ⚠️**内容完整**：确保生成的内容没有被截断。

### 验证方法（每次生成 JSON 后必执行）⭐

**使用专用接口**：`python "${SKILL_DIR}/scripts/file_tools.py" from_json <JSON文件完整路径>`

**该接口的功能**：
1. **自动检测**：尝试用 `json.load()` 解析 JSON 文件
2. **自动修复**：如果格式有误（单引号、尾逗号、括号不匹配等），会**自动修复**并写回原文件

**⚠️ 重要提示：每次生成 JSON 文件后，都必须立即验证，验证后必须再次检查内容！**

由于自动修复功能可能会**改变或丢失部分原始内容**（例如修复时可能截断、合并或误改某些字段值或嵌套结构），因此在每次运行 `from_json` 后，必须立即 Read 修复后的 JSON 文件，仔细检查以下内容是否符合原本的生成意图：
- ✅ 所有必填字段是否存在且值正确
- ✅ 数组/对象的嵌套结构是否符合结构模板
- ✅ 字符串内容是否被意外截断或修改
- ✅ 数值、布尔值等类型是否正确

如果发现修复后的内容和结构与预期不符，必须立即使用 `Write` 工具将**正确的完整内容**重新写入该 JSON 文件，然后再次运行 `from_json` 验证，直到格式和内容都完全正确为止。

## 工作流程

### Step 1：读取查新报告

**`Read`** `${输出目录}/materials/prior-art-report.md`，它包含了待申请专利项目的查新结果，客观评估论文本专利是否具备足够的创造性高度，确定本专利最具技术价值和市场保护意义的重点技术特征。

### Step 2：生成初始专利组合

**`Read`** `${输出目录}/materials/claim-tree-v1.json`，它完整记录了待申请专利项目的所有技术特征。基于 claim-tree-v1.json 和查新报告，**直接生成专利组合**。不要生成多个候选方案，而是直接给出你认为最合理的拆分方案。

#### 2.1 对每个独立权利要求进行独立性判断

对 claim-tree-v1.json 中的每个独立权利要求 `M_i`（即**每个最浅层键**），检查：

- **是否有区别技术特征？**：该模块在查新报告中是否被识别为区别特征？
- **是否可独立实现？**：去掉其他模块后，该模块能否完整工作？
- **与其他模块的依赖关系？**：数据流依赖？接口调用依赖？还是必须包含对方的具体实现？
- **与其他模块是否共享核心技术特征？**：如果共享，是否满足单一性要求（可在同一件专利中）？

#### 2.2 决定拆分方案

根据上述判断，直接决定：
- 拆成几件专利？
- 每件专利包含哪些独立权利要求？
- 每件专利的标题是什么？
- 哪些技术点建议作为商业秘密保护？
- 哪些技术点只是常规实现，可被忽略？

**判断依据**：
- 如果某个独权属于行业常规实现，没有突出的创新点 → 不申请专利
- 如果两个独权之间**缺乏共同的技术特征** → 应当分不同专利
- 如果两个独权共享**核心技术基础** → 可以在同一件专利中以多个独立权利要求形式出现
- 如果某个独权的创新点容易被规避 → 单独成件，保护范围更聚焦

#### 2.3 为每件专利确定权利要求树

对每件专利，直接从 claim-tree-v1.json 中引用对应独权的权利要求树，不要重新构建或改写。

**规则**：
- 如果一件专利只包含一个独权 → 直接使用该独权的权利要求树，不做任何改动
- 如果一件专利包含多个独权 → 将各独权的权利要求树合并，补一个总标题即可，各独权内部的技术特征表述保持不变
- 对抗优化阶段才调整权利要求的表述和布局，Step 2 阶段只做引用和合并

#### 2.4 保存初始专利组合方案

将 Step 2 生成的初始专利组合方案保存到```${输出目录}/materials/portfolio-initial.json```。

### Step 3：权利要求树优化

基于 Step 2 生成的专利组合，通过多轮对抗来发现并封堵专利布局中的漏洞。博弈针对的是 Step 2.3 确定的每件专利的权利要求树（直接引用 claim-tree-v1.json），多件专利同时进行博弈。

**【重要】**：每一轮攻防结束后，必须立即将该轮的完整过程保存到独立文件```${输出目录}/claim-optimization/R{n}.json```并验证格式，其中 `n` 为轮次编号（1-6），**验证不通过不能进入下一轮攻防！**

**⚠️ 必需字段清单**（生成JSON时必须包含以下所有字段，缺一不可）：

**顶层必需字段**：
- `round_number` (number): 轮次编号（1-6）
- `title` (string): 该轮标题
- `subtitle` (string): 副标题
- `principle` (string): 原理说明
- `round_summary` (string): 该轮总结
- `patents` (array): 专利攻防记录数组

**patents数组中每个对象的必需字段**：
- `patent_id` (string): 专利编号（P1, P2, ...）
- `patent_title` (string): 专利标题
- `status` (string): 状态（"通过"/"需改进"/"放弃"）
- `attacks` (array): 攻击记录数组
- `defense` (object): 防守回应对象

**attacks数组中每个攻击对象的必需字段**：
- `type` (string): 攻击类型
- `details` (string): 攻击详细描述
- `conclusion` (string): 攻击结论
- `attack_successful` (boolean): 攻击是否成功

**defense对象的必需字段**：
- `response` (string): 统一回应说明
- `actions_taken` (array): 采取的行动列表
- `improvements_to_claim_tree` (array): 权利要求树改进记录数组

**improvements_to_claim_tree数组中每个改进对象的必需字段**：
- `type` (string): 改进类型

- `before` (string): 修改前表述
- `after` (string): 修改后表述

#### 博弈规则

**攻击方（红方）**：扮演竞争对手的专利律师，目标是找到专利组合中的漏洞，设计规避方案或无效理由。不能改变技术方案本身，只能寻找权利要求撰写上的漏洞。

**防守方（蓝方）**：扮演本专利的代理师，目标是封堵漏洞、优化权利要求布局。不能发明新的技术特征，只能调整权利要求的表述和布局。

#### 第一轮：现有技术覆盖攻击

这是博弈的起点。如果独权被现有技术覆盖，后面的规避路径和保护范围讨论都没有意义。

**攻击方**基于查新报告，对每件专利的独立权利要求进行特征比对：

```
针对专利 P_j 的独立权利要求：

特征 1: [特征描述] → 对比文件 D1 的第X段公开了相同/相似特征
特征 2: [特征描述] → 对比文件 D2 的第Y段公开了相同/相似特征
特征 3: [特征描述] → 未发现公开

攻击结论：
  - 如果特征1+特征2都被公开 → 该独权缺乏新颖性，需要增加区别特征
  - 如果特征1被公开但特征1+特征2的组合未被公开 → 需要论证组合的非显而易见性
  - 如果所有特征都未被公开 → 新颖性稳固
```

**防守方**回应：

```
针对现有技术覆盖的防守：
  - 如果独权被覆盖：
    → 首先判断是否有修改价值：
       - 检查 claim-tree-v1.json 中该独权是否还有未被公开的子特征可以提升到独权
       - 评估这些子特征是否具有足够的创新性和实用性
    → 如果有修改价值（存在可用的区别特征）：
       - 从 claim-tree-v1.json 中提取该独权的其他技术特征，加入独权
       - 或者调整独权的表述角度，强调查新报告未覆盖的技术效果
       - 修改后的独权：...
    → 如果**没有修改价值**（所有子特征都已被公开或缺乏创新性）：
       - **放弃该权利要求**
       - 标记为"不具备申请价值"，不纳入最终专利组合
       - 记录放弃原因："现有技术已完全覆盖，无可用的区别技术特征"
  - 如果独权稳固：
    → 确认该专利的新颖性基础和区别技术特征
```

**本轮特殊规则**：如果防守方成功封堵了所有现有技术覆盖，该专利通过本轮，后续博弈轮次中不再重复检查现有技术覆盖。如果某专利的独权无法通过本轮（即无论如何调整都被现有技术覆盖），标记为"需重新考虑是否申请"。

#### 第二轮：规避路径攻击 —— 基于全面覆盖原则（第一次）

**核心原理**：根据全面覆盖原则，标的产品必须包含权利要求中的全部技术特征（ABCD），且特征间的关系与权利要求描述一致，才构成侵权。如果独权包含特征ABCD，竞争对手只需实现ABCE（替换D），即不构成侵权。**独权中的每一个特征都是规避的突破口**。

**攻击方**对每件专利，基于全面覆盖原则找出 2~3 条可能的规避路径：

```
针对专利 P_j 的独立权利要求，其特征为 A + B + C + D + ...：

规避路径 1（替换特征X）：
  - 目标特征：[独权中的某个具体特征，如"通过螺栓连接"]
  - 攻击思路：如果竞争对手不采用 [具体技术手段A]，而是改用 [替代方案B]...
  - 可行性分析：替代方案B是否能达到相似的技术效果？实现难度如何？
  - 全面覆盖判定：替代方案B是否在字面上不同于特征A？如果是，则不构成字面侵权
  - 结论：该规避路径 [可行/部分可行/不可行]，因为...

规避路径 2（省略特征Y）：
  - 目标特征：[独权中的某个特征]
  - 攻击思路：如果竞争对手的实现方案中不包含特征Y，而是通过其他方式达到相同效果...
  - 全面覆盖判定：缺少特征Y → 不满足全面覆盖 → 不构成字面侵权
  - 结论：...

规避路径 3：
  ...
```

**防守方**对每条规避路径进行回应：

```
针对规避路径 1 的防守：
  - 如果规避路径可行（字面上不同）：
    → 调整独权表述，将 [具体技术手段A] 上位概括为 [更宽泛的技术概念]
      例如："通过螺栓连接" → "通过可拆卸连接件固定"
    → 在从权中分别保护 [技术手段A] 和 [替代方案B] 两种具体实现
    → 修改后的独权：...
  - 如果规避路径不可行：
    → 说明为什么替代方案B无法达到相同效果（技术原理层面的分析）
    → 这本身就是专利创造性的体现，记录到交底书的"有益效果"中
```

#### 第三轮：规避路径攻击 —— 基于全面覆盖原则（第二次）

第二轮做了上位概括和从权补充后，本轮检查是否还有遗漏的全面覆盖漏洞，以及上位概括是否引入了新问题。

**攻击方**针对第二轮修改后的权利要求继续攻击：

```
针对专利 P_j（基于第二轮修改后的权利要求）：

新的规避路径 1：
  - 攻击思路：既然你把 [具体手段A] 概括成了 [宽泛概念]，那我用 [完全不同的技术路线] 来实现相同功能...
  - 可行性分析：该技术路线是否能绕开宽泛概念的覆盖？
  - 结论：...

新的规避路径 2（上位概括过宽风险）：
  - 攻击思路：你把 [具体手段A] 概括得太宽了，对比文件 D3 可能已经公开了这个宽泛概念...
  - 现有技术重新比对：[分析]
  - 结论：上位概括导致新颖性受损 / 上位概括合理

新的规避路径 3：
  ...
```

**防守方**回应：
- 如果上位概括过宽被现有技术覆盖 → 收窄表述，在从权中保留较宽的范围作为优选实施例
- 如果发现新的规避路径 → 继续封堵

#### 第四轮：规避路径攻击 —— 基于等效侵权原则（第一次）

**核心原理转换**：经过两轮全面覆盖攻击后，字面侵权的漏洞基本堵死。现在切换到等效侵权原则——即使字面上不完全覆盖，但如果"以基本相同的手段、实现基本相同的功能、达到基本相同的效果"，仍构成侵权。**攻击方现在要寻找的是：能否用一种不满足等效判定四项标准的方式来实现类似功能？**

**攻击方**在第三轮封堵的基础上，重点攻击等效侵权的边界：

```
针对专利 P_j（基于第三轮修改后的权利要求）：

等效替换攻击 1：
  - 目标特征：[独权中的某个特征，如"通过可拆卸连接件固定"]
  - 攻击思路：既然你用了上位概括 [宽泛概念]，那我用 [具体替代方案D'] 来实现相同效果
  - 等效判定分析：
    → 手段是否基本相同？[分析]
    → 功能是否基本相同？[分析]
    → 效果是否基本相同？[分析]
    → 本领域普通技术人员是否无需创造性劳动即可联想到？[分析]
  - 如果四项中有一项不满足 → 不构成等效侵权 → 规避成功
  - 结论：该规避路径 [可行/部分可行/不可行]，因为...

特征细化攻击 2：
  - 目标特征：[独权中界定过于细致的特征]
  - 攻击思路：该特征的界定过于具体（如"温度范围为50-60℃"），我用 [45-55℃] 或 [65-75℃] 替换
  - 等效判定分析：范围边界附近的数值替换是否构成等效？
  - 结论：...

等效替换攻击 3：
  ...
```

**防守方**回应：

```
针对等效替换攻击的防守：
  - 如果等效判定四项都满足（确实构成等效）：
    → 这是好事，说明该规避路径在侵权判定时仍会被认定为侵权
    → 记录到交底书中，说明该专利的保护范围覆盖了等效替换
  - 如果等效判定有一项不满足（可能不构成等效）：
    → 在从权中增加对该替代方案D'的明确保护
    → 或者调整独权中该特征的表述，使其覆盖范围更宽
      例如："温度范围为50-60℃" → "温度范围为40-70℃"（如果claim-tree-v1中有依据）
    → 修改后的独权/从权：...
  - 如果特征界定过于细致：
    → 上位概括该特征，扩大保护范围
    → 在从权中保留具体数值范围作为优选实施例
```

#### 第五轮：规避路径攻击 —— 基于等效侵权原则（第二次）

第四轮做了等效边界处理后，本轮检查是否还有遗漏的等效漏洞，以及第四轮的处理方式是否引入了新问题。

**攻击方**针对第四轮修改后的权利要求继续攻击：

```
针对专利 P_j（基于第四轮修改后的权利要求）：

新的等效替换攻击 1：
  - 攻击思路：你在从权中增加了对 [替代方案D'] 的保护，但还有一种 [替代方案D''] 没有覆盖...
  - 等效判定分析：D'' 是否满足等效四项标准？
  - 结论：...

新的等效替换攻击 2（从权层次问题）：
  - 攻击思路：你的从权引用关系存在跳跃，导致某些组合没有覆盖到...
  - 分析：[具体说明]
  - 结论：...

新的等效替换攻击 3：
  ...
```

**防守方**回应：
- 如果发现新的等效漏洞 → 继续封堵
- 如果无法找到新的有效攻击路径 → 本轮提前结束

#### 第六轮：权利要求质量检查

经过前面五轮的微观攻击（逐特征找漏洞、逐等效边界检验），现在从**整体视角**审视每件专利的权利要求撰写质量。这是对前面所有修改的系统性审查。

**攻击方**从以下维度进行检查：

```
针对专利 P_j（基于第五轮修改后的最终权利要求）：

1. 从属权利要求布局：
   - 引用关系是否形成清晰的层次结构？
   - 是否存在跳跃引用导致保护范围出现空白？
   - 是否充分展开了各种实施方式？
   - 重要替代方案是否都有对应的从权保护？

2. 术语和表述一致性：
   - 同一概念在不同权利要求中是否使用了一致的术语？
   - 技术特征的描述是否符合专利法规定的撰写规范？
   - 是否存在模糊不清或可能产生歧义的表述？

3. 多件专利间协调性：
   - 各专利的保护范围是否存在重叠或空白地带？
   - 竞争对手是否可以利用专利间的缝隙实现类似功能？
   - 核心专利与外围专利的配合关系是否合理？

4. 单一性验证：
   - 该专利包含多个独立权利要求时，它们是否共享特定技术特征？
   - 经过前面五轮修改后，是否引入了破坏单一性的新内容？
```

**防守方**回应并优化：

```
针对质量检查的回应：
  - 移除独权中的非必要技术特征（移入从权）
  - 进一步上位概括独权中的具体特征
  - 补充遗漏的必要技术特征
  - 修复从权引用关系，消除跳跃引用
  - 统一术语表述，消除歧义
  - 补充缺失的从权实施方式
  - 调整专利间保护范围的协调性
  - 如违反单一性 → 拆分专利或调整独权
  - 输出最终优化的权利要求树
```

## 关键要求
- **真实性原则**：所有分析必须严格基于项目的真实文件，不得凭空捏造或臆测不存在的技术方案
- **术语标准**：必须采用所属技术领域的通用技术术语，优先使用国家标准、行业标准规定的规范名词，以及国际专利分类表（IPC）中的标准技术术语。国家有统一规定的自然科学名词，应当采用官方统一术语；无官方规定的，可采用本领域约定俗成的表述，不得自行编造非通用词汇。禁止使用口头俗称、网络热词、行业黑话、非技术类表述替代专业术语。
- **通俗易懂**：用清晰直白的语言描述技术方案，确保非本领域技术人员也能理解，避免空泛赞美、营销口号、万能句式、正确废话等具有“AI味”套话。
